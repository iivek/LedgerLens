# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What LedgerLens is

An offline, on-device invoice/receipt extractor (photo → structured JSON) built as a model-compression portfolio project. Read [ledgerlens_project_spec.md](ledgerlens_project_spec.md) before substantive work — it defines scope, models, the weekend plan, and hard rules. The headline deliverable is the Pareto grid: accuracy vs bits/size/latency, one point per compression variant.

## Commands

```sh
uv sync                      # core env (harness, metrics, synthetic gen); --extra data|render|gpu as needed
uv run pytest                # test suite (fast, no models needed)
uv run pytest tests/test_metrics.py -k line_items   # single test
uv run ledgerlens eval --runner hf|llamacpp --split <jsonl> --tag <variant> --host <where>
uv run ledgerlens convert cord|sroie|personal
uv run ledgerlens synth --n 2000
```

GPU-side scripts (`scripts/`) need `--extra gpu` and real GPU compute this Mac doesn't have — don't try to run them locally. In practice they run on **Kaggle's free GPU tier** (T4; `NvidiaTeslaP100` is incompatible with modern PyTorch wheels — always set `machine_shape: "NvidiaTeslaT4"` in kernel-metadata.json), driven by chunked kernel pushes since one Kaggle session can't fit a full multi-hour labeling/training job. Order: `teacher_label.py` → `train_sft.py` → `quantize_ptq.py` / `qat_torchao.py` / `prune.py` → `export_gguf.py` → `bench_efficiency.py`.

This machine has multiple named Kaggle accounts under `~/.kaggle/tokens/` for quota pooling. **Always use `~/.kaggle/kaggle-as <account> <args>`, never bare `kaggle`** — it verifies identity before running and restores the prior credential after, so it can't silently run as (or clobber) another project's account on this shared machine. This repo's account is recorded in `.kaggle-account` (`johannvekstr`, with `ioannesio` as an automatic quota-exhaustion failover — see the chunked-driver pattern below). A `kaggle` CLI call failing with a permission/identity error is very likely a credential swap by another project sharing this machine, not a real problem with your kernel/dataset — recheck with `kaggle-as` before assuming something broke.

## Architecture: the contracts that hold everything together

- **`src/ledgerlens/schema.py` is frozen.** `Extraction` (pydantic) + `PROMPT` are the single contract shared by the harness, teacher labeling, SFT targets, and the Android app. `android/.../Prompts.kt` embeds a byte-identical copy of `PROMPT` inside the Qwen ChatML wrapper — if one changes, the other must, but after baselines are run neither should (it invalidates all comparisons).
- **Normalization before comparison** (`normalize.py`): predictions and gold both pass through separator-tolerant number parsing, ambiguity-safe date canonicalization, and currency aliasing. Metric changes belong there, not in `metrics.py`.
- **Runners return raw text, not parsed JSON** (`runners/`): JSON validity is itself a metric, so parsing failures are counted in the harness, never swallowed. The `llamacpp` runner talks to `llama-server` so laptop/phone rows measure the same runtime that ships. `mock` exists so the whole pipeline runs modelless in tests.
- **Unified data format** (`data/unified.py`): every source (CORD, SROIE, synthetic, personal holdout) converts to one JSONL-plus-images layout; downstream code never knows the source. CORD lacks vendor/date/currency (null); SROIE lacks line items/tax — they complement each other.
  - **Known caveat, found by visual inspection, not fixed:** ~13% of SROIE training images (81/626, checked directly) are full-page office scans (>15MP, up to 35MP) with large blank margins and occasional handwritten filing numbers — not phone photos, a different capture modality than CORD's mostly hand-held shots. Since MIN_PIXELS/MAX_PIXELS caps *total* pixel budget regardless of source resolution, these get downscaled to the same budget as a tightly-cropped image, leaving the actual receipt text proportionally smaller/blurrier within that budget. Left as-is (no auto-crop implemented) rather than engineering a fix without GPU access to validate it helps — but if SROIE accuracy on the eval set is unexpectedly weak after training, check whether it's concentrated in this large-scan subset before concluding the model just "isn't good at SROIE."
  - **Known caveat, found by MD5 image hashing, quantified not fixed:** 7 of SROIE test's 347 images are byte-identical to a *different-numbered* image in SROIE train (e.g. `sroie_test_X51009008095` == `sroie_train_X51006008095`) — a duplicate-scan quirk in the source SROIE dataset itself, not a bug in `unified.py`'s split logic (confirmed no ID-level train/test overlap at all; this is purely image-content duplication under different IDs). The distilled model got all 7 right, but excluding them entirely moves SROIE `total_em` by ~0.1pt (0.9683→0.9676 HF fp16, 0.9654→0.9647 GGUF q4_k_m) — checked directly, not assumed, after this looked suspicious enough to verify. Not worth building a dedup mechanism for a sub-0.1pt effect; re-check if any future SROIE result seems to hinge on a small sample-count edge case.
- **Metrics score only what a source annotates** (`metrics.py:ANNOTATED_FIELDS`): a sample's `source` (`cord`/`sroie`/`synthetic`/`personal`) determines which fields are scored — e.g. SROIE gold never has line items, so a model that correctly extracts them isn't penalized for it. `harness.py` passes `source` through automatically. Extending to a new source requires adding its annotated-field set here first.
  - **Known caveat, deliberately not "fixed":** this masking is per-*source* (CORD annotates tax as a field-type), not per-*sample*. A CORD receipt with gold `tax: null` could mean either "genuinely no tax line" or "the annotator skipped it" — there's no per-sample signal in the dataset to tell which, so a model correctly reading a real tax line the annotator missed scores 0 there, and a model that outputs null everywhere gets free both-null credit. CORD's ~55% tax EM partly reflects this, not just reading accuracy. Not fixable without better upstream annotations; report null vs. non-null gold subsets separately if this matters for a specific claim, rather than trusting the blended number as pure accuracy.
- **Synthetic augmentation has a severity budget** (`data/synthetic/augment.py:SEVERITY_BUDGET`): each of the five phone-photo degradations draws its own severity and is scaled down once cumulative severity exceeds the budget, so realistic single/double effects stay strong but five-at-once never renders text fully illegible (this was a real bug — early unrestrained stacking produced unreadable training images).
- **Results are append-only CSVs keyed by `tag`**: `results/results.csv` (accuracy, from the harness) joins `results/efficiency.csv` (size/RAM/tok/s/latency, from `bench_efficiency.py`) on `tag`. One tag = one Pareto point. Per-sample raw outputs persist in `runs/<tag>/predictions.jsonl` for audit.
- **Training reuses eval code**: `train_sft.py:build_messages`/`make_collator` are imported by `qat_torchao.py`; teacher labels carry both teacher output and gold plus an agreement flag so blend policy (`gold` | `teacher` | `teacher-agree`) is chosen at train time without re-labeling. `build_messages`'s heavy imports are all deferred into `main()`, so the blend-policy logic itself is unit-testable without torch (`tests/test_train_sft.py`) — keep it that way.
- **Personal holdout has no source of truth to convert** (`data/personal.py`): unlike CORD/SROIE/synthetic, a human has to supply gold labels for real photographed receipts. First run scaffolds blank label JSON per photo; second run (after hand-filling) builds the split. Unknown/typo'd label keys raise loudly — deliberately stricter than `Extraction`'s default leniency (which stays lenient for parsing model output, where tolerating stray fields is correct).
- **Android** (`android/`): Compose UI + JNI over llama.cpp's `mtmd`. Superseded by `mobile/` (React Native, cross-platform) — kept for reference, not the active app.
- **`mobile/`**: React Native app (Android verified on real hardware; iOS blocked on this machine lacking full Xcode). `src/model/prompt.ts` embeds a byte-identical copy of `PROMPT` inside the same Qwen ChatML wrapper `android/Prompts.kt` used — if one changes, the other must. Extraction goes through `llama.rn`'s `initLlama` + `initMultimodal`, with `src/model/schema.ts` porting `schema.py`'s `parse_model_output` (fence-stripping, first-balanced-JSON-object extraction) to TypeScript so on-device parsing tolerates the same malformed output the Python harness does. Category is never model-derived — `CATEGORIES` is a fixed user-picked list, by explicit product decision, not a technical limitation. `src/model/scanQueue.ts` decouples capture from extraction: `ScanScreen`'s capture button (and the dev test-image button) enqueue immediately and leave the camera live for the next shot, while a module-level singleton worker processes the queue strictly one item at a time — there's one shared `llama.rn` context, so no real parallelism to exploit, only backgrounding-within-the-app (switching tabs) while it grinds through however many were queued. The queue lives outside React state (a plain subscribe/`useSyncExternalStore` store, same singleton pattern as `extract.ts`'s memoized model context) specifically so it survives tab navigation regardless of screen-mounting behavior. This replaced the earlier single-item capture→review→retake flow entirely — there's no freeze-frame/Retake step anymore, only enqueue-then-discard.
  - **Known caveat, measured directly on physical hardware (`common_perf_print` from an actual successful run), not fixed:** end-to-end extraction on a mid-range Android phone (no GPU/NPU path available — `libOpenCL.so` absent, so `llama.rn` correctly falls back to its best CPU-only SIMD variant) took **11.3 minutes** for one receipt: `prompt eval time = 674192.77 ms / 1351 tokens (2.00 tokens/sec)` vs `eval time = 5582.50 ms / 53 runs (9.49 tokens/sec)` — i.e. 99% of the wall-clock time is the image/prompt prefill, not answer generation, which runs at a perfectly normal speed once it starts. Root cause: the `mmproj` (vision tower) ships as `f16`, not quantized like the `q4_k_m` LLM weights — llama.cpp's vision-tower quantization support is far less mature than its LLM decoder path — so this is a full-precision dense ViT forward pass on CPU with zero acceleration. Confirmed, not assumed: `results/efficiency.csv`'s `sft2b-teacher-agree-q4km-{cord,sroie}` rows (the "0.99GB / ~3.4s e2e" numbers) have `host=macbook-m1pro-metal` — Apple Silicon's Metal GPU backend, which llama.cpp accelerates natively for both LLM decode *and* the vision encoder. Those numbers are real, but they describe a GPU-accelerated Mac, not phone-equivalent CPU-only hardware; citing them as "on-device speed" for a phone would be dishonest, and the ~200x gap (3.4s vs 11.3min) is exactly the order of magnitude a dense fp16 workload going from GPU to unaccelerated CPU would produce. Fixed a related-but-smaller bug on the way: `initMultimodal`'s `image_min_tokens`/`image_max_tokens` were left unset, so `mtmd` picked ~4000 image tokens by default — over 3x the ~1280-token ceiling `MIN_PIXELS`/`MAX_PIXELS` implies the model was ever trained/measured at. Bounded to 256–1280 (`src/model/extract.ts`), which is still correct and necessary, but did not fix the fundamental fp16-CPU-vision-encoder bottleneck. Not fixed: would need either a quantized mmproj (nontrivial extra GPU compression work, unvalidated — worth trying `image_max_tokens` down toward the 256 floor first, as a free experiment, since prefill cost should scale roughly linearly with image token count) or accepting a GPU/NPU-only real-time story.
  - **Resolution, confirmed on qualifying hardware (2026-08-16):** tested the same build on a Nothing Phone (3) (Snapdragon 8s Gen 4 / SM8735, Adreno 825 — two generations past llama.cpp's verified floor). `librnllama_jni_v8_2_dotprod_i8mm_hexagon_opencl.so` loaded and initialized without the Honor phone's crash. Real `common_perf_print` from a successful run: `prompt eval time = 14193.16 ms / 665 tokens (46.85 tokens/sec)`, `eval time = 4489.79 ms / 105 runs (23.39 tokens/sec)`, **total time = 18777.78 ms** — an ~36x speedup over the CPU-only 778G+ run (23x on prefill specifically, 2.5x on generation), and in line with published academic numbers for accelerated on-device VLM inference (MobileVLM-3B on a OnePlus 13R via llama.cpp: ~21s total, arXiv:2507.08505). Extraction accuracy on a real SROIE test image (`sroie_test_X00016469670`, gold from `data/processed/sroie_test.jsonl`) was an exact match on every scored field: vendor `OJC MARKETING SDN BHD`, date `2019-01-15`, total `193` — plus a correctly-read line item SROIE doesn't even annotate (`KINGS SAFETY SHOES KWD 805`, $193, matching the total). One honest miss: currency guessed `SGD`; the `SDN BHD` suffix is Malaysian, `MYR` would fit better — unscored either way since SROIE has no currency ground truth. **Conclusion: on-device is genuinely viable, but chip-gated** — needs real Snapdragon 8 Gen 1+ hardware with a working OpenCL/Hexagon path, not just "a phone."
  - **Root-caused, 2026-08-17 (was "not yet root-caused" as of earlier the same day):** on this same Nothing Phone 3, extraction against the identical SROIE image and identical staged `model.gguf`/`mmproj.gguf` (byte-verified via `md5sum`, unchanged since the 2026-08-16 success above) went from 100% reliable to consistently returning an empty/null extraction (`vendor: null`, hallucinated `currency`, `total: 0`) on 8 consecutive attempts. File/state-level causes were ruled out first (md5-verified image and model files, `am force-stop` + relaunch, full device reboot, a second unrelated image failing the same way) before the real cause surfaced: `dumpsys thermalservice` showed **`Thermal Status: 3`/SEVERE**, CPU cores at 79.6–99.9°C and GPU cores pinned at 99.9°C — battery temp (34-46°C, checked earlier in the session) was a misleading proxy that undersold how hot the SoC actually was. Corroborated by a controlled comparison, not just the thermal reading alone: identical code and model files run on the Android emulator (thermally unconstrained, CPU-only, `hw.ramSize` bumped from the default 2G to 6G in `~/.android/avd/<name>/config.ini` — 2G OOM-killed mid-extraction on the ~2.3GB combined model+mmproj) produced the *correct* result on the same image. Two `extract.ts` fixes landed alongside this investigation (checking `initMultimodal`'s previously-ignored boolean return + calling `context.isMultimodalEnabled()`, forcing `use_gpu: false`) — genuine gaps worth closing, but not what actually explained the symptom. **Self-correction, worth keeping in mind for future native-level debugging:** an earlier theory in this same investigation — that `/proc/<pid>/maps` showing zero `mmproj` occurrences (vs. `model.gguf` appearing twice) "proved" the vision tower never loads — was wrong. The emulator run reproduced that identical zero-occurrence pattern while still producing a correct result, and a read of `rn-mtmd.hpp`/`rn-llama.cpp` showed every load/tokenize path already checks return values and throws on failure. Vision-tower weights most likely load via `read()` into a heap buffer rather than `mmap()`, so absence from `/proc/maps` by filename was never good evidence either way. **Debugging method that actually worked, when logcat and Metro's terminal both failed to surface React Native's own `console.*` output:** connect to Metro's CDP endpoint directly — `curl http://localhost:8081/json/list` for the device's `webSocketDebuggerUrl`, then a Python `websockets` client sending `Origin: http://localhost:8081` (needed to avoid HTTP 401) plus `Runtime.enable`/`Log.enable`, listening for `Runtime.consoleAPICalled`/`Runtime.exceptionThrown`. This is what surfaced the real JS-side error text during later debugging and should be the first resort, not the last, next time device logs go dark. Not yet understood at the mechanistic level: *why* thermal throttling degrades vision-encoder output to null/hallucinated fields specifically, rather than just running slower — plausibly a precision/correctness effect of aggressive DVFS on the ViT forward pass, but that is a hypothesis, not confirmed.
  - **Confirmed on the physical device itself, 2026-08-24 (a week after cooling off):** same Nothing Phone 3, same staged `model.gguf`/`mmproj.gguf`, same test image, `libOpenCL.so` still not declared (CPU-only fallback) — extraction produced an exact-match result (`WESTERN EASTERN STATIONERY SDN. BHD`, `MYR · $7.42`) with live `dumpsys thermalservice` readings of 34–53°C throughout (`Thermal Status` LIGHT at most), a direct contrast with the SEVERE/99.9°C readings during the failure above. This closes the loop the emulator-only comparison couldn't: the same hardware that produced null/hallucinated output while overheated produces correct output once cool, with nothing else changed. Full edit → categorize → save flow also re-verified end-to-end on-device, confirmed via a direct SQLite query against the app's own database rather than trusting the UI alone.
  - **GPU path re-verified and re-enabled, same day (2026-08-24):** with the phone cool, tested acceleration in two isolated steps rather than flipping both at once. Step 1: re-enabled `libOpenCL.so` in the manifest but left `initMultimodal`'s `use_gpu: false` (the vision tower forced to CPU, as it had been since 2026-08-17) — result was **slower** than pure CPU-only (2.5min vs ~2.1min) and pushed `Thermal Status` to MODERATE, confirming the vision-tower prefill (not the LLM decode) is the real bottleneck, consistent with the ~99%-in-prefill breakdown documented above. Step 2: flipped `use_gpu: true` for the vision tower too — the theory behind that original `false` (a `/proc/maps` check "proving" `mmproj.gguf` never loaded on GPU) had already been walked back as unreliable evidence in the 2026-08-17 investigation, and the real failure mode that day was thermal, not this flag. Three consecutive runs with GPU enabled for both LLM and vision tower: **31s (cold model load), then two more each finishing inside a 1s poll window (well under 14s, warm)** — all three exact-match correct, all three `Thermal Status` LIGHT throughout, zero exceptions in a live CDP console capture. This lines up with the original 2026-08-16 18.8s measurement and confirms it's reproducible, not a one-off. `extract.ts` and the manifest comment both carry this history; `use_gpu: false` for multimodal is retired as a fix for a symptom (thermal throttling) it was never actually treating.
  - **Third device, 2026-08-31 (a HONOR REA-NX9, Snapdragon 7 Gen 1 / Adreno 644):** `libOpenCL.so` disabled pre-emptively for this device before ever installing a GPU-enabled build on it — `/sys/class/kgsl/kgsl-3d0/gpu_model` and `ro.vendor.qti.soc_id` were checked first, found Adreno 644 (mid-range 6-series, same family as the confirmed-crashing 642L), not the 750+/8-series flagship tier the accelerated path is verified safe on. CPU-only extraction against the SROIE `sroie_test_X00016469670` image (gold: vendor `OJC MARKETING SDN BHD`, date `2019-01-15`, total `193`) was an exact match on every field across two consecutive runs, plus the same correctly-read unannotated line item (`KINGS SAFETY SHOES KWD 805`) seen on the Nothing Phone 3's very first success — and the same honest currency miss (`SGD` guessed, `MYR` fits the `SDN BHD` suffix better), confirming that's a stable model behavior on this input, not device-specific noise. Full edit → categorize → save flow re-verified end-to-end, confirmed via direct SQLite query. **Real, clean-measured latency: 5min 20s** (screen kept awake throughout via periodic wake keyevents to rule out this OEM's aggressive Always-On-Display/Doze policy silently throttling a backgrounded app — see below), `Thermal Status` NONE throughout, so this is genuine compute time, not throttling. Confirms the CPU-fallback path scales down gracefully (correct, just slower) on mid-range hardware, and that the manifest's per-device GPU-safety judgment call is a real, load-bearing decision, not just defensive boilerplate — this device would very plausibly have hit the same SIGABRT crash as the 778G+ if the accelerated build had been installed on it.
  - **OEM power-management gotcha found the same session (HONOR/Magic UI):** this device's Always-On-Display would activate and effectively freeze all adb-driven UI inspection (`uiautomator dump` returns near-empty content scoped to `com.hihonor.aod`, not the app) within roughly a minute of no touch input, *despite* `settings put system screen_off_timeout 1800000` and `dumpsys deviceidle disable` both being set — standard AOSP power settings that fully solved this on the Nothing Phone 3 did not solve it here. `svc power stayon true` (stay-awake-while-charging) helped but the device still dozed at least once during a ~50-minute unattended stretch, escalating all the way to the secure lock screen (fingerprint/PIN), which blocked all further adb inspection until physically unlocked — a real, hard blocker for headless testing on this OEM's software, not present on stock/near-stock Android (Nothing Phone 3) or the emulator. Workaround used for a clean timed measurement: a periodic no-op `input keyevent KEYCODE_WAKEUP` every ~15s during polling, touching only the wake state, never the app's own UI.

## Hard rules (spec §10 — non-negotiable)

- Every published number must come from the harness/bench scripts, reproducibly. Never hand-write results into README or writeups.
- Never imply production deployment or real users. Label laptop-CPU demos honestly as such.
- Dataset licenses (`DATA_LICENSES.md`) are verified against primary sources, never assumed from a search-engine summary or an adjacent code repo's license file (a real near-miss: a downloader script's MIT license is not the dataset's license). SROIE's dataset-level license is unconfirmed and stays flagged research-use-only until verified with the RRC/ICDAR organizers.

## Environment notes

- macOS, no GPU, no Android SDK. Locally runnable: tests, synthetic generation (uses system Chrome or Playwright), CORD conversion, mock-runner evals.
- Large artifacts (`data/`, `models/`, `runs/`) are gitignored; never commit datasets or weights.
- **Model recovery (local copies deleted 2026-10-08 to free disk):** the merged SFT HF model (`models/sft2b-teacher-agree-merged/`, 4.4GB `model.safetensors` + config/tokenizer files) is the Kaggle dataset `johannvekstr/ledgerlens-sft2b-teacher-agree` (byte-sizes verified identical before deletion) — restore with `~/.kaggle/kaggle-as johannvekstr datasets download johannvekstr/ledgerlens-sft2b-teacher-agree -p models/sft2b-teacher-agree-merged --unzip`. The LoRA training checkpoints (`checkpoint-{100,150,180}/`, mostly `optimizer.pt`) are in the `johannvekstr/ledgerlens-sft-run` kernel output (`kernels output`); only the final 70MB adapter is kept locally. The GGUFs in `models/gguf/` are **not** on Kaggle — they were converted locally via `third_party/llama.cpp` from the merged model, and `q4_k_m` + `mmproj` are the shipping/Pareto artifacts, so keep them. `models/stock-gguf/` re-downloads from Hugging Face.
